# 笨笨 / Keystone 生活叙事玩法设计

> 面向后端的设计输入。目标不是增加选择弹窗，而是让聊天里的普通一句话，变成世界里的长期后果。
> 当前代码基线：E:\agent_core（keystone-life-sim / world / attention / proactive / memo / roleplay）。

## 0. 一句话

把“一个会自己生活的小世界”升级成“一个玩家会惦记、会后悔、会想回来看后来”的生活叙事沙盒。

核心不是选 A 还是选 B，而是：

> 玩家随口说的一句话，被系统记成承诺、期待、边界或误解；世界在之后的时间里有代价地回应它。

## 1. 当前诊断

现有 life-sim 已经具备很好的地基：

- 有真实时间、体力、心情、金钱、物品、关系、承诺、计划、待办
- 有 director / fate / 延迟效果 / 镇志 / 风闻
- 有 NPC 经济、关系、婚姻、生死
- 有 attention 决定什么时候开口
- 有三层记忆和 history/memory 检索
- 有 roleplay 的隐藏状态维度

现在缺的不是“更多引擎”，而是三样东西：

1. 玩家的话没有稳定地变成世界状态（承诺只有 agent 自己主动记，普通聊天容易说完就散）
2. 后果缺少可被玩家读懂的“回声”（世界变了，但玩家不知道为什么）
3. 缺少一个真正的中心戏剧问题（每天都有事发生，但没有一条让人追着看的主线）

一句话：现在更像一个认真运转的 world sim，还不是一个有戏剧张力的 story engine。

## 2. 设计原则

### 2.1 选择在对话里，不在 UI 里

玩家不会点“我选择支持他”。他只会说：

- “早点关吧，别撑了。”
- “你要去就去，我不管你。”
- “林叔的事你自己看着办。”
- “随便你。”

系统要提取的不是选项，而是：

- 期待：我希望你怎样
- 允许：你可以怎样
- 边界：我不接受你怎样
- 态度：我嘴上说随便，但其实在意

这些成为隐藏的 commitment / constraint / tone，不弹窗。

### 2.2 后果可以晚到，但必须可读

隐形的选择不能配隐形的后果。

后果至少通过三种渠道之一被玩家感知：

- 他下一句话里的细节
- 他的日记 / 朋友圈
- NPC 的说法 / 镇上的变化

不是加“好感 +5”提示，而是让玩家自己拼出来：原来是因为我那天那句话。

### 2.3 没有正确答案，只有代价

每个关键节点两边都合理，两边都有损失：

- 陪玩家，还是守店
- 帮林叔，还是完成答应玩家的事
- 说实话，还是先瞒着
- 留下，还是去追线索

不要设计“善良选项 / 自私选项”。要设计“你更在乎什么”。

### 2.4 低频高权重

大部分对话应该是低压力日常。

- 微选择：每轮都有，影响语气和记忆，不改变命运
- 中选择：每周 2–3 次，改变计划、金钱、关系
- 大选择：每 2–4 周 1 次，不可逆，改变故事走向

不要把每句话都变成考试，否则玩家会累。

### 2.5 世界不围着玩家转

玩家不在的时候，NPC 也要做事。

- 他会错过一些事
- 别人会对他有要求
- 他会在玩家和别的人/事之间取舍
- 玩家不能看全所有内容

这样玩家才会觉得：这是一个世界，不是一个服务。

### 2.6 不惩罚缺席

错过可以留下痕迹，但不要惩罚。

- 不扣好感
- 不锁内容
- 不让他冷暴力
- 他会适应，会失望，但不会报复

真正的“嫌烦”是连续冷淡后的自然降频，不是系统惩罚。

## 3. 核心循环

1. 观察：主动消息 / 朋友圈 / 日记 / NPC 的话
2. 解读：他需要什么？他在瞒什么？这句话是不是在试探我？
3. 回应：语气、建议、承诺、拒绝、追问、沉默
4. 世界结算：隐藏地改变计划、金钱、健康、关系、NPC 行动
5. 回声：第二天/几天后，通过行为、日记、NPC、物件露出
6. 更新理解：玩家修正对他的认识，产生“后来呢”

关键：第 4 步不告诉玩家，第 5 步才让玩家感觉到。

## 4. 三层选择

| 层级 | 频率 | 例子 | 后果 |
|---|---|---|---|
| 微选择 | 每轮 | 语气、调侃、关心、回避 | 心情、安全感、他下一次说话的防备程度 |
| 中选择 | 每周 2–3 次 | 建议关店、答应帮他、拒绝借钱 | 计划、金钱、体力、NPC 关系 |
| 大选择 | 每 2–4 周 | 是否追旧车票、是否卖店、是否说出秘密 | 故事分支、不可逆损失、长期关系 |

实现上不要新增“选择 UI”。三者都从聊天中提取，只是影响面和寿命不同。

## 5. 机制清单

### P0：先做，决定好不好玩

#### 5.1 潜在承诺账本（Latent Commitment Ledger）

**问题**：现在只有 agent 自己调 life(promise) 才会记承诺，普通聊天里“我明天给你带伞”可能说完就散。

**做法**：

- 每轮对话后，异步提取 0–1 条“可能成为承诺/期待/边界”的话
- 必须由 agent 自己决定 accept / decline / defer，不能系统替它答应
- 记录：原话、类型、触发条件、到期时间、状态、证据
- 到期时由世界结算，并由 agent 决定是否提起

**注意**：不要扫关键词。不要把所有“我会”都当承诺。只记“有代价、可验证、与某个未来时刻相关”的话。

**好玩点**：玩家会发现自己随口一句“别淋雨”，他真的在雨天带了伞；或者他答应了但没做到，后面要解释。

#### 5.2 取舍账本（Tradeoff Ledger）

每当两个合理需求冲突：

- 守店 vs 陪玩家
- 帮林叔 vs 完成承诺
- 省钱 vs 买药
- 去追线索 vs 留在安全的地方

记录：

- 他选了什么
- 放弃了什么
- 代价是什么（钱/时间/体力/关系）
- 谁知道这件事

**不要**把代价写成数值面板。用可见的世界变化表达：店营业额、NPC 态度、他第二天的疲惫、日记里一句没说完的话。

#### 5.3 回声账本（Echo Ledger）

每个重要选择生成 1–3 条未来回声：

- 触发时间（几小时后 / 第二天 / 三天后）
- 触发条件（玩家上线、聊天提到相关词、NPC 来访、天气变化）
- 呈现面（他的消息 / 日记 / 朋友圈 / NPC 对话 / 世界事件）
- 线索强度（轻/中/明确）

回声不是任务提示，而是让玩家事后能拼出因果。

**验收**：玩家在 3 天内至少能说出一次“原来是因为我那天说……”。

#### 5.4 一条中心戏剧问题

不要每天随机撒事件。选一个 2–4 周的问题：

- 旧书店租约要到期
- 1987 年旧车票的主人是谁
- 林叔的病他在瞒什么
- 镇上要修路，旧书店可能被拆

所有系统往这个问题上汇：经济、健康、NPC、天气、节日、关系。

**判断标准**：玩家会主动问“后来呢？”，而不是只问“今天有什么新内容？”。

### P1：让世界有层次

#### 5.5 三层真相

同一件事至少有三种版本：

- 他告诉玩家的版本
- 他日记里的版本
- NPC / 镇上流传的版本

系统保留客观世界事实，但角色可以不知道、误解、隐瞒。

**不要**给玩家一个“真相面板”。让玩家自己判断谁在说谎，或者谁也只是不知道。

#### 5.6 第三者视角

让 NPC 主动告诉玩家一些他不会说的事：

- 林叔：“他最近总在店里待到很晚。”
- 张姨：“他前天来问过借钱的事。”
- 老赵：“那张车票他看了很久。”

这比系统旁白更自然，也能把玩家从“只看他”拉进镇子。

#### 5.7 竞争性请求

让两个 NPC 同时需要他：

- 林叔需要他帮忙看店
- 玩家希望他早点回家
- 老赵约他去旧货市场

玩家只能影响，不能命令。他可能拒绝玩家，也可能对 NPC 失约。

**好玩点**：玩家会意识到自己的话有分量，但不是命令。

#### 5.8 照片作为证据 / 物件

照片不只是聊天附件：

- 他会怎么看这张照片
- 会不会发朋友圈
- 会不会误读玩家的意思
- 会不会因此改变计划
- 几天后照片出现在日记里

物件也一样：旧车票、旧书、修好的门、买给玩家的东西。让物件跨天存在。

#### 5.9 仪式与等待

保留低频固定仪式：

- 早上一条主动消息
- 晚上一篇日记
- 每周一张照片 / 一次共同的事

但内容必须变化，不能变成打卡。

仪式的作用是制造“等待”和“回来看看”，不是奖励。

#### 5.10 错过与不可逆

- 某些事件只在特定时间窗口发生
- 玩家没看到，就真的错过
- 之后通过他的一句话 / 日记 / NPC 提起
- 不补发，不惩罚

**注意**：不要让玩家觉得“错过就完了”。错过应该制造真实感，不是 FOMO。

### P2：锦上添花

#### 5.11 误解与修复

他可能误解玩家的语气：

- 玩家说“随便”，他当真
- 玩家开玩笑，他受伤
- 玩家关心，他听成控制

然后有修复过程：解释、道歉、冷一会儿、再说话。

**不要让误解随机发生**。要基于真实歧义和角色性格。

#### 5.12 他的“项目”

他有一个自己的小项目：

- 修书店的门
- 整理后院旧书
- 找车票主人
- 攒钱买洗衣机

玩家可以支持、忽视、泼冷水。项目有自己的进度和挫折，不是玩家任务列表。

#### 5.13 季节 / 节日 / 天气压力

用现有 season/weather/festival：

- 雨天生意差
- 节日要进货
- 冬天生病
- 房租/水电固定支出

让选择有物质基础，不只是情绪。

#### 5.14 每周回声

每周一次“回看”：

- 他的日记 / 一封信 / 一张照片
- 里面提到这周发生的事
- 包括玩家错过的、他隐瞒的、NPC 说过的

不是总结面板，是一段有语气的叙事。

#### 5.15 可回看的“选择收据”

后端保留每个关键选择的：

- 当时有哪些替代方案
- 他/玩家知道什么
- 放弃的成本
- 后来谁提起过

这不是给玩家看的 UI，而是让后续对话能保持一致，不出现“明明选了 A 却像 B”。

#### 5.16 安静的日常

允许一整天没有大事。

- 他只是在店里理书
- 玩家可以聊，也可以不聊
- 没有“今日任务”

安静的日子会让关键事件更有重量。

## 6. 三条可落地的故事弧

### 弧 A：旧书店的租约（推荐第一条）

**中心问题**：为了保住书店，他愿意牺牲什么？

- Day 1：房东通知涨租，他在聊天里随口提了一句
- Day 2：老赵提出借钱，但有条件；林叔说可以帮忙，但会欠人情
- Day 3：雨天，店里没生意；玩家可以建议关店、借钱、卖书
- Day 4：他做了选择，经济和关系开始变化；日记里出现没对玩家说的压力
- Day 5：NPC 从不同角度告诉玩家一些事
- Day 6：第二次选择，和第一次的后果冲突
- Day 7：暂时解决或悬置，留下下一章钩子

**关键**：没有“正确融资方案”。借钱伤关系，卖书伤记忆，关店伤生意。

### 弧 B：1987 年的旧车票

**中心问题**：有些过去，是否应该被翻出来？

- 车票夹在旧书里
- 林叔看到后反应不对
- 镇志里有一条旧记录
- 玩家可以让他去查，也可以让他别管
- 追查会揭开一个旧人/旧事，影响林叔和他的关系

**关键**：不是解谜游戏，没有“正确答案”；知道真相可能让所有人更难受。

### 弧 C：林叔的病

**中心问题**：尊重他的隐瞒，还是拆穿？

- 林叔咳嗽，说没事
- 笨笨发现了，但答应不说
- 玩家从别处听说
- 选择：告诉别人 / 陪他瞒着 / 直接问林叔

**关键**：每个选择都出于善意，但都有代价。

## 7. 7 天竖切（最小可玩验证）

目标：不做新 UI，只验证“聊天 → 隐藏状态 → 延迟回声”能不能让人想追。

### Day 1

- 早上主动消息提到房东涨租
- 玩家随意回应；系统提取一个潜在承诺/态度
- 晚上日记提到“今天没敢跟他说”

### Day 2

- 老赵提出借钱，笨笨在聊天里试探玩家
- 玩家建议影响 accept/decline/defer
- NPC 对白埋下“老赵不是白帮忙”

### Day 3

- 下雨，林叔需要帮忙，店里也有事
- 笨笨自己做取舍；玩家可能不知道全部

### Day 4

- 后果出现：钱、体力、NPC 关系、店里状况
- 日记出现一句和聊天不一致的话

### Day 5

- 玩家可以从 NPC 或朋友圈发现异常
- 有一个“要不要追问”的微选择

### Day 6

- 第二次选择，和 Day 3 的后果对撞
- 没有完美解

### Day 7

- 一段长日记 / 一封信 / 一次谈话
- 回收至少 3 个回声
- 留下下一章问题

### 竖切验收

- 3 个有代价的关键节点
- 1 个秘密/信息差
- 至少 4 次跨天 callback
- 0 个选择弹窗
- 玩家能复述“我哪句话造成了什么”

## 8. 和 agent_core 的挂接点

建议优先在 `keystone-life-sim` 内做，不急着加新引擎。

| 能力 | 用途 |
|---|---|
| `life` 工具 / life.db | 承诺、计划、项目、关系、物品、日记、帖子 |
| `director.rs` / `fate` | 中心戏剧问题的出题、延迟效果、不可逆事件 |
| `world_pending_effects` | 回声/后果延迟落地 |
| `life_promises` | 现有承诺账本，可扩展为 commitment |
| `relations.rs` / `npc_social.rs` | NPC 竞争性请求与反应 |
| `mood.rs` / `traits.rs` | 语气、心理状态、误解与修复 |
| `keystone-attention` | 决定什么时候让回声浮出，不要定时轰炸 |
| `keystone-proactive` | 主动消息、间隙追话、夜间沉默 |
| `keystone-memo` | 长线记忆、旧事回捞 |
| `keystone-world` | 开放环、变化、镇志、风闻 |
| `keystone-roleplay` | 隐藏关系/状态维度，不做可见好感条 |
| `keystone-session` | 对话原文，用于回声证据和一致性检查 |

### 重要边界

- 世界事实必须由确定性代码保存，LLM 只负责提取建议和说话。
- 不要让 LLM 即兴决定“他其实没借钱”这种世界状态。
- 每个关键选择有且只有一个可审计的 receipt。
- 回声不能凭空生成；必须引用已有的选择/承诺/世界变化。

## 9. 建议数据模型（MVP）

可以放在 life.db，不一定新建库。

### life_story_thread

- id
- title
- central_question
- state: seeded / active / climax / resolved / abandoned
- start_day / deadline_day
- stakes_json
- created_ms / updated_ms

### life_story_beat

- id / thread_id
- due_ms
- beat_kind: setup / complication / choice / consequence / reveal / finale
- trigger_json（时间、天气、NPC、玩家上线、关键词）
- status: pending / fired / missed / consumed
- payload_json

### life_commitment

- id / source_turn_id
- raw_text
- kind: promise / request / boundary / expectation
- decision: accepted / declined / deferred
- due_ms / trigger_json
- status: open / kept / broken / released
- evidence_json

### life_echo

- id / source_kind / source_id
- due_ms
- surface: chat / diary / post / npc / world
- hint_strength: 1–3
- text_hint（给 agent 的提示，不是给玩家的台词）
- status: pending / surfaced / consumed

### life_choice_receipt

- id / choice_id
- chosen_json
- alternatives_json
- known_by_json
- opportunity_cost_json
- later_references_json

### life_secret

- id / thread_id
- holder（谁在瞒）
- content
- reliability
- reveal_conditions_json
- revealed_to_json

## 10. 后端接口/调试面

不建议把隐藏状态直接暴露给前端玩家。

### 内部

- `story_thread_status`：供 agent 自己看当前主线/节奏
- `story_echo_due`：attention 取到期回声
- `story_commitment`：记录/关闭承诺
- `story_receipt`：选择收据

### 调试（仅本地/观测台）

- `GET /api/story/status`
- `GET /api/story/threads`
- `GET /api/story/echoes`
- `GET /api/story/receipts/:id`

玩家前端最多看到自然语言，不看到表。

## 11. 指标与验收

### 先看定性

找 5 个玩家跑 7 天，问：

1. 你记得自己做过什么选择吗？
2. 有没有哪件事你觉得“是因为我那天说的”？
3. 你有没有想知道“后来呢”？
4. 你有没有后悔过某个回复？
5. 你有没有觉得被惩罚/被强迫？

### 定量

- `echo_ack_rate`：回声出现后，玩家是否主动回应/追问
- `callback_recall_rate`：玩家能复述跨天因果的比例
- `thread_return_rate`：离开后因主线回来的比例
- `diary_open_rate`：关键日记打开率
- `npc_ask_rate`：玩家主动问 NPC 的比例
- `regret_rate`：玩家表达“当时不该”的比例
- `perceived_random_rate`：玩家觉得“莫名其妙”的比例
- `emotional_labor_rate`：玩家觉得“累/被索取”的比例

### 红线

- 玩家觉得“所有话都必须小心” → 过度设计
- 玩家觉得“世界随机惩罚我” → 因果不可读
- 玩家觉得“他只是在演剧本” → 一致性失败
- 玩家觉得“没什么可做” → 玩家动词不足

## 12. 反模式

- 选择弹窗 / 好感度条 / 每日任务 / 能量条
- 每句话都改变命运
- 用随机事件制造“戏剧性”
- 让 LLM 编造世界事实
- 缺席惩罚/冷暴力
- 过度解释因果，玩家没有拼图空间
- 把玩家当中心，NPC 只当背景
- 所有照片都变成剧情道具
- 用大量文本替代真正的选择

## 13. 实施顺序

### 第一步（1–2 周）

1. story_thread + beat 最小表
2. commitment 提取（异步、0–1 条/轮、agent 决定）
3. echo 账本 + 1 条 7 天弧
4. 只做聊天/日记/NPC 三种回声面

### 第二步（1 周）

1. 选择收据 + 机会成本
2. 三层真相/一个秘密
3. 竞争性 NPC 请求
4. 调试端点 + playtest

### 第三步

1. 照片/物件连续性
2. 每周回声
3. 误解/修复
4. 季节/节日压力

## 14. 开放问题

- 玩家除了聊天，还应该有什么动词？（建议先不加 UI，用“建议/拒绝/追问/约定”四种意图）
- 允不允许角色对玩家说谎？如果允许，真相层怎么保证公平？
- 真 time 节奏下，玩家错过一周怎么办？是否提供“补看日记”而不是补事件？
- story 状态是每会话、每角色，还是每个玩家？多角色/多租户边界要提前定。
- 作者写弧 vs generator 生成：第一条弧必须手写，后面再半自动。

## 15. 最终判断

这些机制做到，会让它从“有氛围的陪伴 demo”变成“有记忆、有代价、有回声的生活叙事”。

但“好玩”不会自动从系统里长出来。真正决定成败的是：

1. 中心问题是否让人在乎
2. 选择是否有真实代价
3. 回声是否可被玩家拼出来
4. 玩家是否真的有非聊天动词
5. 角色是否有一致性

系统已经够多了。接下来缺的是作者性、节奏和少量关键节点。
